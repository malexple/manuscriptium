# Manuscriptium — требования к приложению

> Рабочее название: **Manuscriptium** (место где создаются манускипты).
> Альтернативы: Slate, Cinnabar, Flint, Mica.
> Версия документа: 0.1 (draft)

## 1. Видение

Manuscriptium — десктопное и мобильное приложение для управления знаниями (PKM)
и публикации статей, которое объединяет:

- **«толстое» ядро Trilium** — иерархия, атрибуты, синхронизация, задачи,
  диаграммы, self-hosting «из коробки»;
- **«кровеносную систему» Obsidian** — Markdown-файлы на диске, YAML Front
  Matter, граф связей, Git-интеграцию и плагины;
- **готовый пайплайн публикации** — от заметки до статьи на Hugo/статическом
  сайте без сборки workflow из десятка костылей.

Приложение должно работать **из коробки** и при этом расширяться плагинами.

### 1.1. Проблема (боли пользователя)

1. Trilium мощен, но не даёт Front Matter и удобной публикации — из-за этого
   пользователи уходят в Obsidian.
2. Obsidian гибок, но базовый рабочий контур (шаблоны, метаданные, синхронизация,
   Git, публикация) собирается из десятков плагинов и ломается при обновлениях.
3. Разделение инструкций и статей по разным репозиториям, синхронизация через
   внешний сервис и мобильная запись требуют «зоопарка» инструментов
   (Obsidian + Remotely Save + Nextcloud + Forgejo + Obsidian Git + Hugo).
4. Нет единого инструмента, где всё это работает сразу и остаётся переносимым.

### 1.2. Принципы дизайна

- **Толстое ядро, тонкие плагины.** Всё, что нужно 80% пользователей каждый
  день, — в ядре. Плагины — для нишевых задач.
- **Данные принадлежат пользователю.** Markdown-файлы на диске, прозрачная
  структура, Git-совместимость, экспорт без потерь.
- **Local-first.** Полная работа офлайн; синхронизация — надстройка.
- **Скорость как фича.** Мгновенный старт, отзывчивый UI, быстрый поиск.
- **Один инструмент вместо пяти.** Синхронизация, Git, публикация — встроены.

## 2. Пользователи и сценарии

| Персона | Сценарий |
|---|---|
| Автор статей (знакомый) | Пишет заметки, публикует в Hugo через Git, ведёт раздельные репозитории |
| Инженер / homelab | Ведёт инструкции, хранит команды, синхронизирует через self-hosted сервер |
| Исследователь | Собирает заметки со ссылками, строит граф и запросы по метаданным |
| Мобильный пользователь | Быстрая запись с телефона/планшета, чтение, правки на ходу |

Ключевые пользовательские истории (кратко):

- Как автор, я хочу создать заметку из шаблона с заполненным Front Matter
  в один клик, чтобы не копировать YAML вручную.
- Как автор, я хочу, чтобы черновики не публиковались, а готовые статьи
  автоматически попадали в нужный репозиторий и собирались сайтом.
- Как инженер, я хочу держать инструкции и статьи в **разных репозиториях**
  внутри одного приложения и синхронизировать их независимо.
- Как пользователь, я хочу писать с телефона и видеть изменения на десктопе
  без конфликтов и ручных мержей.

## 3. Функциональные требования

Приоритеты: **P0** — MVP, **P1** — первая стабильная версия, **P2** — развитие.

### 3.1. Модель знаний и редактор

- **R1 (P0)** Гибридная структура: иерархическое дерево (папки/заметки, как
  в Trilium) **и** сеть двусторонних ссылок `[[...]]` с графом (как в Obsidian).
- **R2 (P0)** Markdown как формат хранения: `.md` файлы на диске, человекочитаемые,
  пригодные для Git.
- **R3 (P0)** Front Matter (YAML) — **первоклассная встроенная функция**: парсинг,
  валидация по схеме, автодополнение полей, подсветка ошибок в редакторе.
- **R4 (P0)** WYSIWYG-подобный редактор Markdown (split-view или live preview),
  поддержка таблиц, списков задач, кода с подсветкой.
- **R5 (P1)** Атрибуты заметки (как в Trilium) поверх Front Matter: теги,
  произвольные поля, наследование от родителя.
- **R6 (P1)** Встроенные Callout-блоки (Note/Tip/Warning/Danger).
- **R7 (P1)** Продвинутое редактирование таблиц (как Advanced Tables).
- **R8 (P2)** Встроенный canvas/диаграммы и рисование (аналог Excalidraw).

### 3.2. Навигация и поиск

- **R9 (P0)** Полнотекстовый поиск по контенту и метаданным (Lucene), с фильтрами
  по полям Front Matter и по дереву.
- **R10 (P0)** Быстрый переключатель (Quick Switcher) и командная палитра.
- **R11 (P1)** Продвинутый навигатор по дереву: Folder Notes, счётчики заметок,
  закреплённые элементы, сортировка.
- **R12 (P1)** Поиск по вложениям (PDF, изображения) с извлечением текста.
- **R13 (P2)** Граф связей с фильтрами.

### 3.3. Метаданные и запросы

- **R14 (P0)** Встроенный механизм запросов к Front Matter (аналог Dataview/Bases):
  таблицы и списки, построенные на полях заметок.
- **R15 (P1)** Интерактивные элементы для редактирования свойств (переключатели,
  выпадающие списки, поля даты) — аналог Meta Bind.
- **R16 (P1)** Схемы Front Matter для разных типов заметок (статья, инструкция,
  дневник) с валидацией.

### 3.4. Шаблоны и автоматизация

- **R17 (P0)** Система шаблонов (аналог Templater): переменные (дата, заголовок,
  путь), подстановка Front Matter, вставка сниппетов.
- **R18 (P0)** Быстрые действия (аналог QuickAdd): одной командой создать заметку
  по шаблону в нужной папке с нужными полями.
- **R19 (P1)** Автоформатирование (аналог Linter): сортировка полей Front Matter,
  нормализация Markdown, удаление лишних пробелов; запуск по сохранению/по команде.
- **R20 (P1)** Daily notes и шаблоны периодических заметок.

### 3.5. Задачи и планирование

- **R21 (P1)** Списки задач с фильтрами и сроками (аналог Tasks), единый
  дашборд задач по хранилищу.
- **R22 (P1)** Календарь и напоминания.
- **R23 (P2)** Kanban-доски на основе заметок.

### 3.6. Синхронизация и репозитории

- **R24 (P0)** Поддержка **нескольких независимых репозиториев/хранилищ** внутри
  одного приложения (например, «Основное», «Статьи», «Инструкции»), каждое —
  отдельная папка + отдельный Git-remote + отдельные настройки синхронизации.
- **R25 (P0)** Абстрактный слой синхронизации с бэкендами:
    - собственный сервер Manuscriptium (self-hosted, P0);
    - Git (P0);
    - WebDAV/Nextcloud (P1);
    - S3-совместимое хранилище (P2).
- **R26 (P0)** Разделение задач **«синхронизация»** (быстрая, для работы) и
  **«бэкап/версионирование»** (Git) — как два разных режима.
- **R27 (P1)** Разрешение конфликтов: автоматический мерж для текста, ручной
  диалог для бинарных файлов и неразрешимых конфликтов.
- **R28 (P1)** Офлайн-режим с очередью изменений и отложенной отправкой.

### 3.7. Git и публикация (ядро, не плагин)

- **R29 (P0)** Встроенная Git-интеграция (JGit): init, commit, push, pull,
  авто-коммиты по расписанию/событию, статус в UI.
- **R30 (P0)** Управление секретами: токены и SSH-ключи хранятся в защищённом
  хранилище ОС и **никогда** не попадают в репозиторий.
- **R31 (P0)** Пайплайн публикации: заметка с `draft: false` и корректным
  Front Matter → коммит в репозиторий статей → (опционально) триггер сборки
  Hugo/SSG → отчёт о результате в UI.
- **R32 (P0)** Валидация контента перед публикацией: проверка обязательных полей,
  битых ссылок, вложений; ошибки видны в редакторе, а не только в логах CI.
- **R33 (P1)** Экспорт в PDF/HTML/EPUB с профилями оформления.
- **R34 (P2)** Встроенные шаблоны проектов для Hugo/Astro/Next.js.

### 3.8. Вложения и мультимедиа

- **R35 (P1)** Локальные изображения: автозагрузка внешних картинок и сохранение
  рядом с заметкой (аналог Local Images Plus).
- **R36 (P1)** Управление вложениями: переименование, дедупликация, относительные
  пути, проверка целостности ссылок.

### 3.9. Плагины и кастомизация

- **R37 (P0)** Архитектура плагинов на JPMS: отдельные JAR-модули, загружаемые
  через `ModuleLayer` + `ServiceLoader`; точки расширения (API) описаны отдельным
  модулем `Manuscriptium.api`.
- **R38 (P0)** Реестр плагинов: список установленных, включение/отключение,
  версии, зависимости, совместимость с версией ядра.
- **R39 (P1)** Локальная установка плагина из файла/папки; P2 — удалённый каталог.
- **R40 (P1)** Темы оформления и Style Settings через GUI (FlatLaf-темы +
  пользовательские свойства).
- **R41 (P1)** Командная палитра расширяется плагинами (регистрация команд,
  горячих клавиш, пунктов меню).

### 3.10. Мобильность

- **R42 (P0)** Клиент для смартфона/планшета — на выбор: PWA/адаптивный
  веб-клиент к self-hosted серверу (рекомендуется) **или** отдельное мобильное
  приложение.
- **R43 (P0)** Быстрая запись с мобильного (создание заметки из шаблона за 1–2 тапа).
- **R44 (P1)** Чтение и лёгкое редактирование, офлайн-кэш, фоновая синхронизация.

## 4. Нефункциональные требования

- **N1 Производительность:** холодный старт ≤ 2 с на SSD; открытие хранилища
  на 10 000 заметок ≤ 3 с; поиск ≤ 200 мс; UI не блокируется дольше 100 мс
  (тяжёлые операции — в фоновых потоках).
- **N2 Кроссплатформенность:** Windows 10/11, macOS (Intel + Apple Silicon),
  Linux (X11 и Wayland). Java 17+, jlink-рантайм или jpackage-инсталляторы.
- **N3 Надёжность:** атомарные записи файлов, автосохранение, восстановление
  после сбоя; локальные данные не теряются при недоступности сервера.
- **N4 Приватность:** всё работает локально; телеметрии нет по умолчанию;
  сеть — только по явной настройке.
- **N5 Безопасность плагинов:** изоляция по зависимостям и явные разрешения
  (доступ к файлам/сети); см. раздел 6.
- **N6 Доступность:** навигация с клавиатуры, масштабирование UI, контрастные темы.
- **N7 Совместимость данных:** экспорт/импорт Markdown-хранилища без потерь;
  корректная работа с существующими Obsidian-vault (Front Matter, wiki-ссылки).
- **N8 Обновления:** проверка обновлений ядра и плагинов, откат версии.

## 5. Техническая архитектура

### 5.1. Стек

| Слой | Выбор |
|---|---|
| Язык / рантайм | Java 17 (LTS), JPMS |
| UI | Swing + FlatLaf (+ FlatLaf Extras), кастомные компоненты |
| Markdown | Flexmark (парсинг/рендер), свой редактор на JTextPane/RSyntaxTextArea |
| Предпросмотр HTML | JCEF (встроенный Chromium) или Lobo-подобный браузер как fallback |
| Поиск | Apache Lucene |
| Хранение метаданных/индекса | SQLite (Xerial JDBC), FTS5 для быстрых подсказок |
| Git | JGit |
| Синхронизация | собственный сервер (Ktor/Netty) + HTTP/WebSocket протокол |
| Конфигурация | JSON/YAML (Jackson) в per-user каталоге ОС |
| Сборка | Gradle (multi-module), jlink/jpackage |
| Тесты | JUnit 5, TestFX для UI, интеграционные тесты синхронизации |

### 5.2. Модульная структура (JPMS)
graphite.parent
├── graphite.api // публичный API для плагинов (только интерфейсы)
├── graphite.core // модель, хранилище, индексация, поиск
├── graphite.sync // абстракция синхронизации + Git
├── graphite.publish // пайплайн публикации, валидация, SSG-интеграция
├── graphite.ui // Swing/FlatLaf UI
├── graphite.app // точка входа, сборка ModuleLayer для плагинов
└── graphite.plugin.* // примеры и сторонние плагины


Правило: **плагины зависят только от `graphite.api`**, никогда от `graphite.core`/
`graphite.ui`. Это позволяет менять внутренности ядра, не ломая плагины.

### 5.3. Формат хранилища
<vault>/
.graphite/
vault.json // настройки хранилища (remote, sync-режим, схемы)
index.db // SQLite-индекс (регенерируемый кэш)
notes/ // дерево .md файлов — источник истины
...
attachments/
...


Метаданные (иерархия, атрибуты) хранятся **в самих `.md`** (Front Matter + путь)
и дублируются в индексе. Индекс можно пересобрать из файлов в любой момент —
это ключ к переносимости и Git-совместимости.

## 6. Плагинная модель (JPMS) — детали

- Плагин — это JAR с `module-info.java`, реализующий интерфейсы из `graphite.api`
  и регистрирующий их через `ServiceLoader` (`provides ... with ...`).
- Загрузка — отдельный `ModuleLayer` с `Configuration.resolveAndBind`; плагины не
  видят внутренние пакеты ядра (только экспортированные из `graphite.api`).
- Манифест плагина (`plugin.json`): id, version, min/max версия ядра, зависимости,
  запрашиваемые разрешения, точки расширения.
- **Важно:** JPMS даёт модульную изоляцию, но **не является песочницей
  безопасности** (SecurityManager в Java 17 deprecated и удаляется). Варианты
  политики безопасности, которые надо выбрать на этапе проектирования:
    1. **Capability-подход в API:** плагин получает доступ к файлам/сети только через
       сервисы ядра (`FileService`, `NetworkService`), которые проверяют разрешения.
    2. **Изоляция процессов** для плагинов, помеченных как «недоверенные» (P2).
    3. **Подпись плагинов** и whitelist источников (P2).
- Версионирование API: semver, отдельный модуль `graphite.api` версионируется
  независимо от ядра.
- Обновление/удаление плагинов без перезапуска — P2; в MVP — перезапуск.

## 7. MVP (что делаем первым)

Цель MVP: **доказать, что «толстое ядро + Front Matter + Git + публикация»
работает, быстро и из коробки.**

Обязательно в MVP (P0):
1. Дерево + Markdown-редактор + Front Matter с валидацией (R1–R4).
2. Поиск + Quick Switcher (R9, R10).
3. Шаблоны и QuickAdd (R17, R18).
4. Несколько хранилищ + Git-интеграция + публикация с валидацией (R24–R26, R29–R32).
5. Плагинная архитектура с 1–2 демо-плагинами (R37, R38).
6. Мобильный веб-клиент с быстрой записью к self-hosted серверу (R42, R43).
7. Настройки синхронизации, статус, разрешение простых конфликтов (R25, R27).

После MVP (P1–P2): запросы к метаданным, задачи/календарь, продвинутый навигатор,
вложения, темы, экспорт PDF, граф, canvas, каталог плагинов.

## 8. Риски и открытые вопросы

- **Swing и рендеринг HTML:** JCEF тянет за собой тяжёлый рантайм. Нужно решить:
  JCEF как основной предпросмотр или лёгкий HTML-рендер + JCEF как опция.
- **Синхронизация — самая сложная часть.** Нужен протокол и стратегия мержа
  (CRDT? трёхсторонний мерж по файлам? Git как транспорт?). Выбор влияет на
  мобильный клиент.
- **Безопасность плагинов** (см. раздел 6) — надо зафиксировать модель до MVP.
- **Конкуренция:** Kryton, SiYuan, Logseq, Silverbullet — стоит явно
  сформулировать, чем Graphite лучше (скорость, «из коробки», Git+публикация).
- **Мобильность:** PWA vs нативное приложение — влияет на объём работ.
- **Юзабилити Swing:** FlatLaf сильно помогает, но потребуется аккуратный UI-kit
  (иконки, отступы, типографика), иначе будет «выглядеть как 2010».
- **Открытый вопрос:** нужен ли собственный сервер синхронизации в MVP или
  достаточно Git + WebDAV? Это радикально меняет объём.

## 9. Критерии успеха MVP

- Пользователь устанавливает Graphite и за 5 минут создаёт заметку, пишет статью,
  коммитит и публикует — **без установки сторонних плагинов**.
- Холодный старт ≤ 2 с, поиск по 10k заметок ≤ 200 мс.
- Плагин, написанный по документации `graphite.api`, устанавливается и работает
  без пересборки ядра.
- Заметка, созданная на телефоне, появляется на десктопе без ручных действий.
